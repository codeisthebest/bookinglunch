# bookinglunch：企業內部訂餐與取餐管理系統（原型）

員工用手機訂餐，取餐口即時驗證訂餐資格，後台管理名單、菜單與未取餐扣款追蹤。
目前是**可展示的原型**：已支援 LINE LIFF 登入（需設定 channel，未設定時為展示用的模擬登入），尚未串接鼎新 ERP。

## 啟動

```bash
npm install
node scripts/seed.js   # 產生 30 位展示用員工（E001–E030）與當月平日菜單；會清空資料庫 data/bookinglunch.db 再重建
npm start              # http://localhost:3000
npm test               # 單元與 API 測試
```

| 頁面 | 路徑 | 說明 |
|---|---|---|
| 員工訂餐 | `/` | LINE（LIFF）登入；未設定時用員編模擬登入。訂餐、改單、取消、轉讓、委託代領、顯示取餐碼 |
| 取餐口 | `/pickup.html` | 放在現場平板，需用**裝置編號＋裝置金鑰**登入（後台「系統設定」建立；展示資料有 `KIOSK-01`，金鑰 `kiosk-key-demo-0001`）。USB 條碼槍直接掃，瀏覽器支援時可用相機掃碼 |
| 管理後台 | `/admin.html` | 帳號密碼登入，依角色顯示功能。初始帳號 `admin`，密碼見下方「管理員與權限」 |

環境變數：

| 變數 | 說明 |
|---|---|
| `PORT` | 預設 3000 |
| `ADMIN_PASSWORD` | **首次啟動**時建立初始管理員 `admin` 的密碼，預設 `admin`。之後密碼存在資料檔中，改這個變數不會再生效 |
| `DB_FILE` | SQLite 資料庫檔路徑，預設 `data/bookinglunch.db` |
| `DATA_FILE` | 舊版 JSON 資料檔路徑（預設 `data/db.json`）。只用於第一次啟動時自動搬遷，見「資料儲存」 |
| `QR_SECRET` | 動態取餐碼的簽章金鑰（伺服器端）。未設定時每次啟動隨機產生，舊碼重啟後失效（最多影響 60 秒）。多台伺服器共用時必須設成相同值 |
| `LINE_LOGIN_CHANNEL_ID` | LINE Login channel 的 Channel ID。設定後自動切換為 LINE 登入模式 |
| `LIFF_ID` | LIFF 應用的 ID（形如 `1234567890-AbCdEfGh`）。LINE 模式必填 |
| `AUTH_MODE` | 選填，`mock`（模擬登入）或 `line`；未設定時依是否有 `LINE_LOGIN_CHANNEL_ID` 決定 |

## Docker 部署

映像以 `node:22-alpine` 為基底，約 250 MB，以非 root 的 `node` 使用者執行，內建健康檢查（`/healthz`），收到 `docker stop` 會正常關閉。

```bash
cp .env.example .env          # 編輯 .env：至少設定 ADMIN_PASSWORD 與 QR_SECRET
docker compose up -d --build
# 開啟 http://主機:3000（埠號可用 HOST_PORT 調整）
```

- `QR_SECRET` 建議用 `openssl rand -hex 32` 產生。`ADMIN_PASSWORD` 只在**第一次啟動**建立 `admin` 時使用。
- 訂單、員工名單、帳號都存在具名 volume `bookinglunch-data`（容器內 `/data/bookinglunch.db`），**重新部署或重建容器不會遺失，但請定期備份**。
- **只能跑一個實例**：資料庫是單一 SQLite 檔，登入狀態在記憶體中，不要設定多個 replica。容器重啟後後台管理員需重新登入（LINE 員工會自動重新登入，取餐口平板會自動重新上線）。
- **LIFF 需要 HTTPS**：容器本身只提供 HTTP，請在前面放反向代理（Nginx、Caddy、公司的負載平衡器等）終止 TLS 後轉發到 3000 埠。

常用指令（先停止服務再操作資料，避免記憶體中的狀態覆蓋檔案）：

```bash
# 載入展示資料（會清空資料庫，僅限展示環境）
docker compose stop app && docker compose run --rm app node scripts/seed.js && docker compose start app

# 忘記系統管理員密碼
docker compose stop app && docker compose run --rm app node scripts/reset-admin.js admin 新密碼 && docker compose start app

# 備份資料（服務運作中也能執行，取得一致的完整快照，存在 volume 內的 /data/backups/）
docker compose exec app node scripts/backup.js
# 把備份檔複製出來
docker compose cp app:/data/backups ./backups

# 查看記錄
docker compose logs -f app
```

## 管理員與權限

每位管理員有自己的帳號密碼，角色決定能做什麼。權限是最小單位，角色只是權限的組合（定義在 `src/permissions.js`，要新增角色只改那一個檔案）。

| 權限 | 系統管理員 | 營運人員（助理） | 唯讀 |
|---|:-:|:-:|:-:|
| 查看報表、訂單、菜單 | ✅ | ✅ | ✅ |
| 匯出扣款清單 CSV | ✅ | ✅ | — |
| 維護每日菜單 | ✅ | ✅ | — |
| 處理扣款狀態、例外名單 | ✅ | ✅ | — |
| 員工名單匯入、LINE 綁定管理 | ✅ | — | — |
| 系統設定（截止時間、補貼、★ 提前天數、員編位數、手動取餐開關、模擬時間） | ✅ | — | — |
| 取餐口裝置管理 | ✅ | — | — |
| 管理員帳號、操作紀錄 | ✅ | — | — |

- **每次請求都由伺服器檢查權限**，前端隱藏按鈕只是方便，不是防線。停用帳號或調整角色**立即生效**，不必等對方重新登入。
- 首次啟動沒有任何管理員時，會用 `ADMIN_PASSWORD`（預設 `admin`）建立 `admin`（系統管理員）；伺服器啟動時若 `admin` 還在用預設密碼會顯示警告，**上線前務必更改**。
- 密碼以 scrypt 加鹽雜湊儲存，至少 8 個字元；連續登入失敗 5 次鎖定該帳號 15 分鐘。
- 不能停用或降級自己；重設他人密碼或停用帳號時，對方既有的登入會立即作廢。
- 所有成功的寫入操作都會記錄「誰、何時、哪個動作」（不含請求內容，避免寫入密碼），系統管理員可在「管理員帳號」頁查看最近 200 筆。
- 忘記系統管理員密碼：停止伺服器後在主機上執行 `node scripts/reset-admin.js <帳號> <新密碼>`。
- 展示資料（`node scripts/seed.js`）會額外建立 `assistant`（營運人員，密碼 `demo-assistant-1`）與 `auditor`（唯讀，密碼 `demo-auditor-1`），**僅限展示環境**。

## 取餐驗證與取餐口裝置

**動態取餐碼**：員工頁的取餐碼是伺服器簽發的 QR Code，格式 `P.員編.時間窗格.簽章`。

- 每 30 秒換一次，簽章用 HMAC-SHA256，金鑰只在伺服器（`QR_SECRET`），瀏覽器看不到。
- 取餐口驗證簽章與時效（30–60 秒內有效），**截圖轉傳超過 1 分鐘就失效**，竄改員編或簽章一律拒絕。
- 驗證通過後伺服器發一張「取餐憑證」，綁定該員工與這台取餐口、2 分鐘內有效；按「確認取餐」時用憑證，不必在 60 秒內操作完，也不能拿到別台取餐口用。

**手動輸入員編（後備方式）**：忘了帶手機時，可在取餐口輸入員編。這種取餐會在紀錄中標記為「手動輸入（未驗證）」，後台報表有專屬統計與明細欄位可稽核；管理員可在「系統設定」一鍵關閉，關閉後只接受動態碼與委託取餐。

**取餐口裝置登入**：取餐 API 不再開放匿名呼叫。每台平板用裝置編號＋裝置金鑰登入（金鑰只在建立或重設時顯示一次，資料庫只存加鹽雜湊）。平板會記住裝置，伺服器重啟後自動重新上線。後台可停用裝置或重設金鑰，**立即生效**。每筆取餐都記錄是哪一台取餐口完成的。

**委託代領**不變：仍須代領人輸入自己的員編，且必須與訂餐人指定的相符。

## 資料儲存（SQLite）

資料存在單一 SQLite 檔（Node 內建的 `node:sqlite`，不需另外安裝或編譯；需要 Node 22 以上）。相較先前的 JSON 檔：

- **當機或斷電不會損毀資料**：使用預寫式日誌（WAL）與交易，寫到一半中斷只會回到上一個完整狀態；每個操作（訂餐、取餐、轉讓、匯入…）是一個交易，失敗整筆回復。
- **資料庫層的最後防線**：同一人同一天同一餐別只能有一筆有效訂單；一個員編只能綁一個 LINE 帳號；訂單必須屬於存在的員工。
- 可用任何 SQLite 工具直接檢視或查詢（建議唯讀開啟）。資料表：`employees`、`bindings`、`admins`、`kiosks`、`menu_items`、`orders`、`exemptions`、`history`、`config`。

**備份**：`node scripts/backup.js [目的檔]`（預設寫到資料庫旁的 `backups/`）。伺服器運作中也能執行。**不要直接複製運作中的 `.db` 檔**，最新資料可能還在 `-wal` 檔裡。還原時停止伺服器，把備份檔放回 `DB_FILE` 指定的位置，並刪除舊的 `-wal`、`-shm` 檔。

**從舊版 JSON 搬遷**：若先前用過 JSON 版（`data/db.json`），第一次以新版啟動時，資料庫是空的、舊檔還在，會自動搬進 SQLite，舊檔改名為 `db.json.migrated` 保留（不刪除）。搬遷在同一個交易內，失敗會整筆回復並中止啟動。也可手動執行 `node scripts/migrate-json.js <舊檔> [資料庫檔]`。

## Excel 匯入與匯出

後台各處都能直接用 Excel（`.xlsx`），不需要先轉成 CSV。

| 功能 | 位置 | 權限 |
|---|---|---|
| 匯入員工名單（含範本下載） | 員工名單 | 員工名單管理 |
| 匯出員工名單（含 LINE 綁定狀態，不含驗證碼） | 員工名單 | 員工名單管理 |
| 匯入整月菜單（含範本下載） | 菜單管理 | 維護菜單 |
| 匯出某月菜單（格式同匯入，可改完再匯入） | 菜單管理 | 查看報表 |
| 匯出訂單明細＋每日統計（任意區間，最長一年） | 當日報表 | 匯出扣款清單 |
| 匯出某日未取餐扣款清單（含合計，給人事） | 當日報表 | 匯出扣款清單 |

**匯入規則**
- **員工名單**：必要欄位「員工編號」「姓名」（也認「員工代號」「工號」）；選填「部門」或「部門代號」＋「部門名稱」、「驗證碼」。員編欄是數字格式時自動補零（`10412` → `010412`）。有問題的列會略過並回報**與 Excel 一致的列號**，其餘照常匯入。
- **菜單**：必要欄位「日期」「餐別」「品名」「定價」；選填「主菜」「配菜」（頓號或逗號分隔）「蔬菜／湯品」「特殊商品」（★／是）。日期可以是 Excel 日期或 `YYYY-MM-DD`、`YYYY/M/D` 文字；餐別可寫午餐／晚餐／lunch／dinner。檔案裡出現的每一天，當天菜單**整天取代**；**有任何一列錯誤時整份都不匯入**，並列出每一列的問題。
- 活頁簿有多個工作表時，優先讀名為「員工名單」或「菜單」的工作表，否則讀第一個未隱藏的。

**匯出的安全處理**：文字一律存成字串儲存格，開頭是 `=`、`+`、`-`、`@` 的內容也只會被當成文字，不會被 Excel 當成公式執行（CSV 匯出同樣會加單引號防護）；員編欄設為文字格式，保留前導零。

**上傳檔案的防護**：大小上限 10 MB；解壓縮後過大（zip 炸彈）、列數過多、含 `DOCTYPE`／`ENTITY` 的 XML（實體膨脹攻擊）、舊版 `.xls`、有密碼保護的檔案都會被拒絕，並回報清楚的訊息。

## 員編與員工名單

- 公司員編為 6 碼、開頭可能是 0（如 `012003`）。Excel 把員編存成數字再匯出，會變成 `12003`。**系統會把純數字員編自動補零到「員編位數」（預設 6）**，匯入、登入、綁定、轉讓、委託、取餐口輸入都一致處理；含字母的員編（如 `E001`）不受影響。後台可調整位數（0 = 不補）。
- 匯入後會提示「有 N 筆員編已自動補零」。仍建議把 Excel 員編欄位設成「文字」格式再匯出。
- 部門可以放單一「部門」欄，或公司匯出的「部門代號」＋「部門名稱」兩欄（會合併成 `2100 資訊中心`）。

## 菜單與 ★ 特殊商品

- 每個品項有：餐別、品名、定價、主菜、配菜、蔬菜／湯品，以及「★ 特殊商品」旗標。
- ★ 特殊商品須於用餐日前 N 天（預設 3，後台可調）訂購。以日期天數計算：距離用餐日不足 N 天時自動鎖定，員工頁會標示原因，系統不提供人工放行。
- 訂單會記錄下單當時的品名與價格，之後修改菜單不影響已下的單。

## LINE 登入（LIFF）

不使用 LINE Official Account，只需要一個 **LINE Login channel**，免費。

**LINE Developers Console 設定**

1. 登入 [LINE Developers Console](https://developers.line.biz/console/)，建立 Provider（建議用公司名稱）。
2. 在 Provider 底下建立 **LINE Login** channel，Region 選 Taiwan 或 Japan 皆可。
3. 在 channel 的「LIFF」分頁新增 LIFF 應用：
   - Endpoint URL：本系統對外的 **HTTPS** 網址（例如 `https://lunch.example.com/`），LIFF 不接受 http。
   - Size：Full。Scope：勾選 `openid`、`profile`（必須有 `openid` 才拿得到 ID Token）。
   - Bot link feature：Off。
4. 取得 **Channel ID**（Basic settings）與 **LIFF ID**，填入上面的環境變數。
5. 把 channel 狀態從 Developing 切換為 **Published**，否則只有管理員與測試者能登入。
6. 員工入口：把 LIFF URL（`https://liff.line.me/<LIFF_ID>`）做成 QR Code 或內部公告連結即可。

**運作方式**

- 前端用 LIFF SDK 取得 ID Token，**由伺服器向 LINE 驗證**（`/oauth2/v2.1/verify`），不信任前端自報的身分。
- 第一次開啟時員工輸入「員工編號＋姓名」（名單若有「驗證碼」欄位則需一併輸入）完成綁定；之後同一個 LINE 帳號自動登入。
- 一個員編只能綁一個 LINE 帳號；連續失敗 5 次會鎖定 15 分鐘；換手機或誤綁由後台「員工名單」頁解除綁定。
- 啟用 LINE 模式後，員編模擬登入端點會關閉。
- LINE 模式下登入狀態不存在瀏覽器，每次開啟都由 LIFF 重新驗證。

**測試**：`npm test` 以假的 LINE 驗證服務涵蓋綁定、鎖定、冒綁與解除綁定流程。與真實 LINE 的串接需要實際的 channel 才能驗證。

## 已實作的規則

- 僅名單內員工可登入與訂餐；後台可匯入 CSV（欄位：員工編號、姓名、部門，相同員編會更新）。
- 開放訂購**當月**任一天（今天起、有上架菜單的日期）；每天統一截止時間（預設 10:00，後台可改），該日截止前可改單、取消、轉讓；每人每日每餐別（午、晚）限訂一份。
- 公司補貼 33 元（後台可改），員工自付 = 定價 − 補貼（60／70／80 元 → 27／37／47 元）。
- 取餐口：掃動態取餐碼即顯示今日訂餐內容並確認取餐；已取餐不可重複領。
- 委託代領：訂餐人必須先指定代領人員編才會產生委託碼（不受訂餐截止限制，只要該餐尚未過取餐期限即可設定或取消）；取餐口仍須代領人輸入自己的員編，且必須與指定者相符，訂餐人本人也不放行。轉讓或取消訂單時委託一併清除。
- 未取餐判定：午餐 13:00、晚餐 18:20 之後仍未取餐者列入清單。後台可設定例外（出差、請假）免列入。
- 「記錄未取餐」與「實際扣款」分開：清單狀態為 待處理／已送人事／已豁免，可匯出 CSV 給人事確認後再送薪資。
- 報表：總訂餐花費、公司補貼小計、員工自付小計、各金額級距、午晚餐數量、已取／待取／未取、手動輸入取餐數、扣款合計，以及含部門與取餐方式的當日訂單明細。
- 後台「模擬時間」僅供展示截止與未取餐判定，正式環境請恢復系統時間。

## 原型的假設與限制（待確認）

- 截止時間 10:00 是暫定值；「當月」指與今天同一個月份，下個月的訂餐要等到下個月才開放。
- 未設定 LINE channel 時是員編模擬登入，**沒有真正的身分驗證**，僅供展示。
- **手動輸入員編的後備方式仍可被冒用**：知道同事員編的人可以在取餐口輸入。目前以「取餐口裝置登入＋紀錄標記為未驗證＋後台可稽核／可關閉」降低風險。人臉辨識是否導入尚待法規確認。
- 取餐口平板把裝置金鑰存在瀏覽器（localStorage）以便自動上線，請把平板當成受管的專用裝置，遺失時在後台停用該裝置。
- 動態碼的 QR 圖片仍由 cdnjs 的 qrcode-generator 產生；離線時退回顯示碼的文字內容，條碼槍或手動貼上也能使用。
- LIFF 登入已用模擬的 LINE 驗證服務測過，**尚未用真實 LINE channel 驗證**。
- 不使用 LINE Official Account，因此沒有推播提醒；未取餐通知管道尚未決定。
- 資料庫是單一 SQLite 檔，適合這個規模（千人、每天約 200 份）；仍只能單一實例執行，不能水平擴充。
